# Compliance Audit — ModelGuard v0.3.0-oss

**Audit date:** 2026-05-24  
**Scope:** ModelGuard backend API (`api/main.py`), storage layer (MinIO), and test suite  
**Frameworks audited:** EU AI Act, GDPR, NIST AI RMF 1.0, SOC 2 Type II, ISO/IEC 27001:2022, OWASP LLM Top 10 (2025)  
**Reference:** `docs/Compliance_Requirements.md`, `docs/Threat_Model.md`

---

## Implemented mitigations

These three controls were implemented in this cycle and close the most acute regulatory, commercial, and operational risk vectors.

| Control | Threat | What was done | Known coverage gap |
|---|---|---|---|
| HMAC-SHA256 batch signature | T-01 | `POST /batch/analyze` now requires `X-Batch-Signature: sha256=<hex>` computed with `BATCH_HMAC_SECRET`. Requests with missing or wrong signatures are rejected 401. | `seed_history.py` writes directly to MinIO, bypassing the API and the HMAC check entirely. Seeded records carry no integrity proof. |
| MinIO object lock (WORM) | T-02 | `modelguard-auditlog` and `modelguard-reports` buckets are created with `--with-lock` and a 30-day GOVERNANCE default retention. Written objects cannot be deleted or overwritten within the retention window. | `ensure_buckets()` in `main.py` creates buckets without object lock if it races ahead of `minio-init` (the backend `depends_on` MinIO health only, not `minio-init` completion). `seed_history.py` has the same unguarded `make_bucket` call. If either path creates the bucket first, WORM is silently absent. |
| Rate limiting | T-03 | `POST /batch/analyze` is limited to 60 req/min per IP (storage exhaustion). `POST /auth/login` is limited to 10 req/min per IP (credential stuffing). Both return 429 on breach. | — |

## Remaining compliance gaps

### EU AI Act

| Obligation | Gap | Reason not implemented |
|---|---|---|
| **Art. 12 — automatic logging** | Audit logs are WORM-locked for objects created via the API. However, there is a startup race condition: `ensure_buckets()` in `main.py` creates buckets without object lock if it executes before `minio-init` completes (the backend service only declares a health dependency on MinIO, not on `minio-init`). If this race is lost, WORM is silently absent and the Art. 12 record-keeping requirement fails without any visible error. Additionally, no structured event log exists for non-batch events (login, model load, startup). | The race condition is an ordering gap in `docker-compose.yml`. A proper fix requires adding `minio-init` as a `depends_on` condition for the backend, or moving bucket creation with lock flags into the backend startup code using the MinIO SDK's object-lock API. Deferred because it requires testing the startup sequence end-to-end. The infrastructure event log is deferred for the same reason as before. |
| **Art. 13 / Art. 11 — technical documentation** | No formal AI system card. `Technical_Design.md` partially covers architecture but not training data provenance, performance metrics, or known limitations in the required format. | Authoring a conformant system card is a documentation task, not a code change. Blocked on product decision about which deployment scenarios to describe (general vs. sector-specific). |
| **Art. 9 — post-market monitoring** | No incident-reporting workflow. No mechanism to notify a supervisory authority within the required timeline following a serious incident. | Requires legal counsel to define what constitutes a reportable incident for ModelGuard's deployment profile, plus an external notification channel. Out of engineering scope until legal review is complete. |
| **Art. 14 — human oversight** | The OE Dashboard displays batch results but has no formal override or acknowledge flow. An operator cannot record a human review decision against a specific batch. | Requires a UI feature (acknowledge button, override form) and a new schema field in the audit record. Significant frontend scope; not part of the threat-model remediation cycle. |

### GDPR

| Obligation | Gap | Reason not implemented |
|---|---|---|
| **Art. 28 — Data Processing Agreement** | No DPA template exists between ModelGuard and its partners. | A DPA is a legal document, not a code change. Requires legal review to draft; cannot be unilaterally generated by engineering. |
| **Art. 5(1)(e) — storage limitation / retention policy** | Full query `input` and `output` text is retained indefinitely in MinIO. No TTL or scheduled deletion exists. | Introducing TTL-based deletion conflicts with the WORM retention just added for T-02: GOVERNANCE-locked objects cannot be deleted within their window. Resolving this requires a two-phase design — short WORM window for tamper-evidence, followed by scheduled expiry — which is a non-trivial storage policy change. Deferred to avoid breaking the T-02 control. |
| **Art. 17 — right to erasure** | No mechanism to locate and delete all objects associated with a specific data subject. MinIO objects are keyed by `partner_id/date/batch_id`, not by `query_user`. | Implementing erasure correctly requires a secondary index (e.g., a database mapping `query_user` → object keys) and a new admin endpoint. This is significant scope and interacts with the WORM lock (GOVERNANCE mode allows admin deletion; COMPLIANCE mode does not). Blocked on the retention policy decision above. |
| **Art. 35 — DPIA** | No Data Protection Impact Assessment has been performed for the systematic monitoring of query users at scale. | A DPIA is a process, not a technical control. Requires a privacy officer or DPO to conduct; cannot be completed by engineering alone. |
| **Art. 33 — breach notification** | No automated workflow to detect a qualifying breach and notify a supervisory authority within 72 hours. | Requires integration with an external notification channel and a defined breach-detection threshold. Depends on the post-market monitoring work blocked on legal review (see EU AI Act Art. 9 above). |

### NIST AI RMF 1.0

| Function | Gap | Reason not implemented |
|---|---|---|
| **Govern** | No written AI risk management policy. RBAC roles exist in code but no formal accountability document describes who owns each risk. | Policy authoring is an organizational task. Engineering can document the technical controls (this document), but the governance layer requires sign-off from product and legal. |
| **Measure** | No historical tracking of Isolation Forest score drift or false-positive rate over time. The model is trained once at startup and never re-evaluated against production distributions. | Implementing drift detection requires storing per-batch score distributions and computing statistical tests across windows. Substantial scope; no stakeholder requirement has been raised yet. |
| **Map** | No formal context mapping against specific deployment sectors (financial services, healthcare, etc.). NIST AI 600-1 controls are not mapped to ModelGuard's specific threat profile. | Context mapping is a documentation task that depends on knowing which customers are deploying the product and in which sectors — information that is not yet available at the MVP stage. |

### SOC 2 Type II

| TSC | Gap | Reason not implemented |
|---|---|---|
| **Security (CC6) — least-privilege access** | The backend uses a single MinIO access key with full read/write access to all three buckets. There is no per-bucket or per-service key restriction. | Creating per-bucket IAM policies in MinIO requires the MinIO admin API or `mc` policy commands. Adds key-management overhead for a single-service architecture; deferred until a multi-service or multi-tenant deployment model is defined. |
| **Security (CC8) — change management** | No change-management process exists for the Isolation Forest model artefact stored in MinIO. The model can be overwritten by any service with the current access key. | Mitigating this properly requires versioning on the `modelguard-detectors` bucket and a promotion workflow (e.g., staging → production). Significant process change; out of scope for this cycle. |
| **Availability (A1) — capacity management** | No SLA is defined. No auto-scaling or disk-usage alerting exists for MinIO. | Requires infrastructure-level configuration (alerting, autoscaling policy) outside the application codebase. Operational responsibility rather than a code change. |
| **Confidentiality (C1) — encryption in transit** | TLS is not enforced between the backend and MinIO (`secure=False` in the MinIO client). Traffic between containers is plaintext on the Docker bridge network. | Acceptable within a single-host Docker deployment where all traffic is on a private bridge. Enabling TLS requires certificate management infrastructure. Should be revisited before any multi-host or cloud deployment. |
| **Processing Integrity (PI1)** | T-01 (HMAC) closes the integrity gap for new API submissions. Historical batches already stored have no retroactive integrity proof. `seed_history.py` writes directly to MinIO and bypasses the HMAC check, so seeded records are unsigned and cannot be distinguished from tampered data by an auditor. | Retroactive signing would require a GOVERNANCE-mode retention bypass and a full rewrite of existing objects. `seed_history.py` is a dev/demo tool; it should not be run against a production MinIO instance. Accepted as a permanent gap for seeded data; all API-submitted records are signed from this point forward. |

### ISO/IEC 27001:2022

| Control | Gap | Reason not implemented |
|---|---|---|
| **A.8.8 — vulnerability management** | No CVE scanning in CI/CD for Python dependencies (`requirements.txt`) or Docker base images. | Requires adding a scanner (e.g., `pip-audit`, Trivy) to the CI pipeline. No CI pipeline currently exists in the repository; out of scope for this cycle. |
| **A.5.30 — ICT continuity** | No backup policy for the Isolation Forest model artefact or audit logs. If the `minio_data` volume is lost, all history and the trained model are gone. | MinIO replication or volume snapshots require infrastructure changes outside the application. The model can be retrained from synthetic data at startup (see `get_detector()`), which partially mitigates loss of the artefact. Full backup policy is an infrastructure task. |
| **A.5.23 — cloud services** | No formal cloud security policy governing MinIO usage. No contractual SLA with the MinIO deployment. | Policy authoring; not a code change. |
| **Model artefact encryption** | No object-level encryption policy for the `modelguard-detectors` bucket. The Isolation Forest pickle is stored in plaintext. | MinIO supports SSE-S3 and SSE-KMS, but enabling them requires a key management service. On a single-host deployment the host filesystem is typically the encryption boundary. Flagged for remediation before any cloud or multi-tenant deployment. |

### OWASP LLM Top 10 (2025)

| Risk | Gap | Reason not implemented |
|---|---|---|
| **LLM06 — Sensitive information disclosure** | Theft reports are accessible to any authenticated user regardless of role (`_ANY_AUTHED`). An analyst at one partner can read reports for a different partner by guessing `partner_id`. | Fixing this requires scoping read access to the owning partner — a RBAC change that would also require the partner identity to be stored in the JWT and compared on every read request. Significant auth refactor; deferred as a follow-on security hardening item. |
| **LLM01 — Prompt injection** | Submitted query `input` fields are fed directly into feature extraction without sanitization. A malicious string engineered to maximize `input_entropy` or `avg_input_length` could skew the Isolation Forest score. | Full prompt-injection defence for an anomaly detector is an open research problem. Structural feature extraction (length, entropy, diversity) is less susceptible than semantic parsing, but not immune. Accepted as a residual risk at this threat model version; documented in `Threat_Model.md` for future review. |
| **LLM10 — Model theft (own artefact)** | The Isolation Forest pickle in `modelguard-detectors` is readable by anyone with the MinIO access key. No object-level access control or download audit log exists for the model artefact. | Mitigating this fully requires per-bucket least-privilege keys (see SOC 2 CC6 above) and enabling MinIO audit logging. Both depend on the access-key refactor deferred above. |

## Summary

| Framework | Controls closed this cycle | Open gaps |
|---|---|---|
| EU AI Act | T-02 (Art. 12 logging integrity) | Art. 11 docs, Art. 9 monitoring, Art. 14 human oversight |
| GDPR | T-01 (Art. 5(1)(d) accuracy), T-03 (Art. 32 technical measures) | Art. 28 DPA, Art. 5(1)(e) retention, Art. 17 erasure, Art. 35 DPIA, Art. 33 breach notification |
| NIST AI RMF | T-01/T-02/T-03 under Manage | Govern policy, Measure drift tracking, Map sector context |
| SOC 2 | PI1 (processing integrity), CC6 partial (rate limiting) | Least-privilege keys, change management, availability SLA, TLS |
| ISO 27001 | A.8.16 (monitoring) | A.8.8 CVE scanning, A.5.30 backup, A.5.23 policy, artefact encryption |
| OWASP LLM | LLM04 (model DoS — rate limiting) | LLM06 report access control, LLM01 prompt injection, LLM10 artefact access |

The three implemented controls close the highest-severity regulatory exposure (EU AI Act Art. 12, SOC 2 PI1) and the most immediate operational risks (storage exhaustion, credential stuffing, falsified batch submissions). The remaining gaps are either organizational/legal tasks that cannot be resolved by code changes alone, or engineering work whose scope exceeds the current remediation cycle and has been explicitly deferred with documented tradeoffs above.
